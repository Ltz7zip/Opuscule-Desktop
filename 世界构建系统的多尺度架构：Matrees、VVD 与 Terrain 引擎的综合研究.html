世界构建系统的多尺度架构

Matrees、VVD 与 Terrain 引擎的综合研究：地图、时间、模拟与协作

摘要

世界构建（worldbuilding）工作站需要在四个目标之间取舍：世界本身的物理/叙事真实性、地图与时间的可读性、多人协作与治理、以及可负担的部署成本。现有系统通常只优化其中一两个目标：Matrees 以 2048² 地形、六类地图要素、多历法事件与提案审核，构建了“世界本体 + 治理”的纵向系统；VVD 以卡片/文档/块与 Yjs 实时协作，构建了“低摩擦 + 横向组合”的文档工作台；Terrain v12 以 450 Myr 板块演化、条件 GAN 与气候/水文链，构建了“物理骨架 + 学习纹理”的地形引擎。本文通过源码级逆向、比较案例研究与设计科学研究，提出“三平面模型”（模拟平面、表示平面、社会平面）解释三者的差异；进一步把 Terrain 拆成物理参考（Pro）、设备端近似（Lite）与服务端摊销生成（Web）三种模型族，并给出 2C2G 控制面 + GPU worker 的部署拓扑。结论是：世界构建系统的竞争力不取决于单一地图生成算法，而取决于能否把世界真值、语义层、时间模型、交互与治理组织成一套可分层交付的架构。

第 1 章 · 绪论：问题、问题域与方法

1.1 研究背景：从“画一张地图”到“维护一个世界”

世界构建工具大致经历了三个阶段。第一阶段是绘图工具：PSD/图片 + 标注，作者用美术能力换表达力。第二阶段是结构化工作台：把地点、事件、人物、历法变成对象，地图与时间线成为可查询的视图。第三阶段是生成式世界引擎：用板块、气候、水文、GAN 生成地形，再把它接入地图与叙事。Matrees 位于第二、三阶段之间；VVD 位于第一、二阶段之间；Terrain 位于第三阶段，但缺少前两个阶段的产品层。

这带来一个核心矛盾：真实度、可读性、协作性与部署成本通常互相拉扯。物理越真实，生成越慢、越难编辑；地图越漂亮，越依赖人工美术；协作越实时，越难保证设定一致性；部署越便宜，越难跑重模型。本文要回答的不是“谁最强”，而是“怎样分层，才能让不同用户在各自预算内得到足够好的世界”。

1.2 研究问题

  1. RQ1（架构）：Matrees 与 VVD 如何分别建模地图、时间线与历法？它们的对象模型、写入路径与协作机制有什么本质差异？
  2. RQ2（感知）：为什么 Terrain v12 已经能生成 2048² 地形，却仍被认为“不如 Matrees 好看”？粗糙感来自算法、尺度、语义还是策展？
  3. RQ3（一致性）：如何让同一份世界数据同时支持局部 2048、全球瓦片、2D 地图与高精度 3D，而不出现“局部/全球不一致”？
  4. RQ4（约束）：如何在 2 核 2G 服务器、核显/手机与服务端 8 秒预算下，保留语义层、时间/演化、交互、协作/发布与视觉风格？

2.3 三条技术谱系

程序化地形谱系从噪声/分形、侵蚀、板块构造到 GAN/扩散。它的评价标准是“地质可信、尺度一致、可复现”；缺点是“像地形”不等于“像地图”。地图工作台谱系从 GIS/图层/要素到插画/PSD；它的评价标准是“可读、可编辑、可发布”；缺点是地形真值弱。协作知识谱系从 Wiki/文档到 CRDT/实时；它的评价标准是“低摩擦、可追溯、可治理”；缺点是空间/时间语义弱。

Matrees 站在第一与第二谱系的交叉：有 heightmap/河流算法，也有 region/city/route 与提案审核。VVD 站在第二与第三谱系的交叉：地图是图像+SVG 注释，文档/卡片/实时协作很强。Terrain 站在第一谱系的深处：物理/生成强，但第二/第三谱系几乎为空。三者的差异不是“功能多少”，而是“站在哪条谱系的深处”。

2.4 研究缺口

  1. 表示缺口：物理地形如何变成“可读地图”（局部尺度、语义、标签、图例），缺少系统化设计。
  2. 时间缺口：地图工作台有历法/事件，地形引擎有 450 Myr，但两者没有共享的时间模型。
  3. 协作缺口：实时 CRDT 与提案治理各有优势，缺少“草稿实时 + 发布审核”的混合模型。
  4. 部署缺口：物理生成、设备端、2C2G 与 8 秒在线被当成同一问题；缺少模型族/算力分层。

本文的贡献正是围绕这四个缺口：三平面框架（表示/时间/协作/部署），以及 Pro/Lite/Web 的模型族与部署矩阵。

2.5 定义与符号

为了避免“地图”“世界”“模型”在不同章节指不同东西，先给出四个工作定义。

定义 1（世界图）：世界图是一个带类型的属性图 G=(V,E,τ,α)。V 是实体（世界、卡片、定义、事件、地图、时间线、资产）；E 是关系（属于、链接、发生于、引用）；τ 是类型；α 是属性。它回答“这个世界由什么组成”。

定义 2（地图文档）：地图文档 M=(B,F,S,T)。B 是基场（heightmap/图片/SeedPack）；F 是要素集合（region/city/pin/river/route/stamp）；S 是样式（palette/light/labels）；T 是瓦片/LOD 树。它回答“这个世界怎么被看见”。

定义 3（时间模型）：时间模型 H=(C,E,Σ)。C 是历法集合；E 是事件/纪元；Σ 是模拟时间切片。它回答“事情何时发生、地图属于哪个时代”。

定义 4（模型族）：模型族 A=(B,Φ,Θ)。B 是共享基场；Φ 是残差/生成器（程序化、GAN、条件生成）；Θ 是参数。它回答“在给定算力下，怎样近似世界”。

2.7 三个命题：尺度、8 秒与误差

命题 1（有效分辨率）：若区域宽度为 L、画布像素为 N，则每像素覆盖 δ=L/N。全球 2048 与局部 2048 的差异不是“像素数”，而是 L。证明是定义展开；推论是：把全球 2048 放大到局部 2048 不会恢复已丢失的高频信息（采样定理/信息损失）。

命题 2（8 秒可行性）：在线生成时间 Tweb=Tlookup+Tbase+Ttile+Tstyle+Tencode。若要求 p95 ≤10s，则必须让 Tbase 接近 0（缓存/预计算）且 Ttile 受控；若 Tbase 包含 450 Myr 全量模拟，命题不成立。8 秒不是算法常数，是“缓存 + 局部生成”的系统约束。

命题 3（摊销误差）：令 zP 为 Pro 参考，zA=Bs+R 为 Lite/Web 近似，则 ||zA−zP|| ≤ ||Bs−zP|| + ||R||（三角不等式）。因此基场误差是下限；再强的局部生成器也不能弥补错误的全球骨架。这条命题直接决定“先共享 SeedPack，再做局部残差”的顺序。

第 3 章 · Matrees：地形工作台的技术深拆

3.1 总架构：世界本体 + 三条链路

Matrees 是 Vue 3 + Pinia + Ant Design Vue Next 的工作台[1][2]，核心不是“地图页面”，而是世界本体（World）+ 对象（Concept/Definition/Event/Calendar/Map/Work）+ 提案网关。地图、时间线、历法不是三个页面，而是三条共享对象模型的链路：地图要素可以链接定义/事件；事件日期依赖历法；所有写入最终经过 proposal/audit。

图 2 · Matrees 的三条链路与提案网关。地图/时间线的“深度”来自共享对象，不是页面功能堆叠。

3.2 地图：三种地图、2048 世界坐标、内容寻址文档

Matrees 支持三种地图：image（上传图片，约 4MB）、PSD（WASM 解析、图层/调色/导出）、vector（在线生成 2048² heightmap + 要素）。坐标系统一为左下原点、x 向东、y 向北、0–2048，编辑器 canvas 坐标与地图世界坐标分离：

// editor canvas -> world (mapSize = 2048)
worldX = editorX
worldY = 2048 - editorY
// general scale
unit = 2048 / mapSize
worldX = editorX / unit
worldY = (2048 - editorY) / unit

地图存储不是一张图，而是内容寻址的文档仓库：manifestHash 指向 chunkHashes、vectorHash、digestHash；上传前先问 missing，只传缺失块，单批 ≤12MB；IndexedDB 缓存草稿；改一条河流不需要重传整张地形。

3.4 地图生成算法：从参数到河流

参数生成的真实字段包括陆地比例 32%、大陆数 2、山脉 70%、群岛度 0.45、风向 25°、模式 tectonic/historical。生成器通过 synth.worker 产出高度图/群系，再做两遍侵蚀（强度默认 0.55）。自动河流不是“画线”，而是：

  1. 以约 size/28 为网格步长，找高于海平面 +0.03 的候选泉眼；
  2. 按高度从高到低排序，做 flow accumulation；
  3. 只保留路径长度 ≥ minFlux（默认 8 格）的河流；
  4. 河流数量夹在 1–12（默认 3）；沿路径雕刻地形，洼地形成湖泊；
  5. 找不到入海泉眼时返回明确错误，而不是静默失败。

区域 tier 1/2/3、道路 smooth/width/closed、印章 scatter 的拒绝采样，共同构成“地图不是背景图，而是可查询的空间数据”。这也是 Matrees 与纯图片地图的根本差异。

3.4.1 写入治理：地图/事件走提案，历法直接写

Matrees 的“世界一致性”不是靠数据库约束自动保证，而是靠提案 + 审核 + baseDocHash 乐观并发。地图/定义/事件写入 proposal；owner/admin 审核；auditor 可读；co-creator 可提案。地图文档用 mapDocHash 做“我改的是哪一版”的并发令牌；服务端发现 baseDocHash 过期就拒绝，避免覆盖别人的修改。

3.5 时间线：年归一化 + 月日分数 + 行 packing

Matrees 的时间线不是时间戳轴，而是“显示历法的年 + 月/日分数”。核心布局公式：

表 2A · Eq.1 变量。x 为像素坐标；y 为显示历法年；m/d 为月/日；W 为画布宽；span=ymax−ymin+1；Dm 为当月天数。

  1. 定范围：取当前显示历法的最小/最大事件年，span=ymax−ymin+1；空世界用默认窗口，避免除零。
  2. 年像素：pxPerYear=W/span；每年等宽，不按实际天数。
  3. 年偏移：x = (y−ymin)·pxPerYear；负数年先归一化到 ymin，不直接 clamp 到 0。
  4. 月日分数：x += (m−1)/12·pxPerYear + (d−1)/Dm·(1/12)·pxPerYear；不要用“月序号×30”。
  5. 区间宽度：width=|xEnd−xStart|；最小 30px，否则点事件不可点。
  6. 行 packing：按开始年排序；每行放不下就换行；最多 5 行；两侧 20px 防碰撞。
  7. 自动缩放/懒加载：最多 8 次 +0.3；初始 100 条，选中前后 25 条，1s 节流。

异常：span=0→用 1；Dm 缺失→回退 30；超长区间→裁剪到当前窗口并标记；负年份/BCE→显示层保留符号，布局层用归一化整数年。

3.6 历法：比例换算 + 显示片段

Eq. 2 · calendar conversion
base=round(ycalratio+baseYear),ycal=round((base−baseYear)⋅ratio)\mathrm{base}=\mathrm{round}\left(\frac{y_{cal}}{ratio}+baseYear\right),\quad y_{cal}=\mathrm{round}((base-baseYear)\cdot ratio)
type 1 纪元：有限区间、不可重叠、仅第一个可无开始、仅最后一个可无结束；type 2 纪年：可无结束、可并存。事件保存 defaultCalendar、bundleCalendar、displayTime[]、yearToZero，前端切换历法只是选片段。

表 2B · Eq.2 变量。base 是服务器绝对年；ycal 是历法年；ratio 是历法年/基准年比例；baseYear 是历法原点。

  1. 建历法：填 type（1 纪元/2 纪年）、baseYear、endYear、ratio、月名/月天数。
  2. 校验：ratio≠0；type 1 的区间不可重叠；只有第一个可无开始、最后一个可无结束。
  3. 写事件：前端只提交历法年/月/日；服务端算 base=round(ycal/ratio+baseYear)。
  4. 回填：为每个相关历法生成 displayTime[] 与 yearToZero；不要在前端重复换算。
  5. 切换：时间线按当前历法选片段；跨历法比较用 base，不用显示年。
  6. 删除/修改：先查事件引用；有引用则迁移或拒绝；不能只删历法。
  7. 验证：同一事件在所有历法下指向同一 base；round-trip 误差 ≤1 年。

异常：ratio 为负/0→拒绝；baseYear 缺失→拒绝；type 1 重叠→拒绝；事件无 displayTime→用 default 历法回填；删除历法有引用→返回冲突而不是静默删除。

3.7 证据、性能与边界

Matrees 的 13 个 JS chunk 共 354,115 字节、115,661 AST 节点、1,104 findings；REA 保留 4,679 call-flow、8,533 closure、75,661 data-flow、317 promise、40 timer，并发现 synth/distance 两个 Worker 与 IndexedDB。静态分析仍有 24,341 个 unknown、覆盖 partial；因此本文把“代码常量/函数”和“运行时观察”分开。

4.4 架构与协作：实时 CRDT vs 提案治理

VVD 是 Next.js App Router + Supabase（Postgres/Auth/Realtime）+ Yjs[3][4]：卡片/文档/块是 document_data 的结构化内容，Yjs 负责正文/块合并，awareness 提供光标/在线状态，Supabase Realtime 做消息同步；发布是 Wiki 快照，支持 private/unlisted/public、密码、自定义域名、页面选择。Matrees 是 Vue/Pinia + 自定义 API：地图/事件/定义写入走 proposal gateway，日历直接写；协作是“提案 + 审核”的异步治理，而不是实时 co-editing。

这两种协作不是“先进/落后”，而是冲突模型不同：VVD 把冲突交给 CRDT，适合“几个人一起写”；Matrees 把冲突交给流程，适合“上千条设定、上万条提案，必须防止设定冲突”。本文的第三路线是“实时草稿 + 发布审核”：草稿层用 Yjs/SSE 低摩擦，发布层用 proposal/audit 保证一致性。

5.4.1 三个最小可行升级

优化不需要一次上全 GCM。先把“时间、泥沙、挠曲”三个最小闭环补上，就能显著提高可信度；它们也是 Pro 的 Ultra 档与 Lite/Web 的训练目标。

∂η∂t=U−∇⋅qs,qs=KQmSn\frac{\partial \eta}{\partial t}=U-\nabla\cdot q_s,\quad q_s=KQ^mS^n

Opt. 2 · flexural isostasy
D∇4w+ρmgw=q,D=ETe312(1−ν2)D\nabla^4w+\rho_mgw=q,\quad D=\frac{ET_e^3}{12(1-\nu^2)}

第 6 章 · 粗糙感诊断：尺度、语义与策展

6.1 全球 2048 vs 画布 2048

2048² 覆盖整个行星时，赤道一像素约 19.6km；一个 4,000km 宽的大陆只有约 205px。Matrees 的 2048² 是地图画布，范围由地图决定；如果覆盖 4,000km，一像素约 2km，细约 10 倍。你们都说 2048，但一个是全球，一个是画布。这是“粗糙感”的第一来源，也是“局部 2048”必须先做局部重算、而不是放大全球图的原因。

图 7 · 尺度错位。把全球 2048 裁一块放大到 2048，不会恢复已经丢失的细节。

6.2 没有语义层，地图只是地形

Matrees 的地图有 region/city/pin/river/route/stamp 六类要素；VVD 有 zones/pins/layers + Card link。Terrain 只有 RGB。人眼判断“这是地图”而不是“地形渲染”，很大程度依赖区域、城市、道路、地名、图例、比例尺。没有这些，即使地形真实，也只是卫星图。

6.3 风格、光照与“数据可视化”

Terrain 的 9 群系色 + NW 单方向山影 + 3px 群系边界，是“数据可视化”而非“美术指导”。Matrees 的视觉优势来自局部画布 + 图层 + 标签 + 可替换底图（image/PSD/vector）+ 作者策展。比较“自动生成”与“人工策展/PSD”的成品，本身就不公平。

6.4 GAN 痕迹与清理

256² 瓦片、208 步长、48 重叠、全局 CDF、despeckle(min_area=150)：这些工程让结果稳定，也会抹掉小岛、产生瓦片重复/接缝、把分布拉回地球。它们不是“算法错”，是“自动管线为了稳定牺牲局部个性”。

6.6 公平比较协议

比较“自动生成”与 Matrees 成品时，至少要对齐：同一区域范围、同一投影、同一像素尺寸、同一标签/图例策略、同一风格预设；否则“Matrees 更好看”可能只是因为它有标签/手绘/PSD。建议做三组实验：① 无标签纯地形；② 有标签/图例的成品图；③ 同一世界局部 vs 全球。每组做盲评（不知道来源）+ 任务（找河流/找海岸/找城市）+ 客观指标。

诊断：粗糙感 = 尺度错位（全球 2048 vs 局部画布）+ 语义缺失 + 美术/光照经验化 + GAN/清理痕迹 + 无交互/策展。它不是单一算法问题；因此优化也不能只靠“再加一个噪声层”。

第 7 章 · 综合架构：世界图、瓦片与三产品线

  2. 多尺度而非单张全球图：局部 2048 + 全球瓦片金字塔；标签屏幕空间。

局部 2048 是“可读性单位”，全球是“瓦片树”，3D 是“同一树的 LOD 表示”。z0 全球总览；z1–z2 区域；z3+ 局部 2048；标签用浏览器屏幕空间绘制；风格由 StyleProfile 控制；Pro 烘焙，Lite/Web 复用。全球地图不应该是一张 8192×8192 的大图，而是按需加载的瓦片。

7.4 时间与历法

把时间拆成三层：模拟时间（Myr/切片）、历法时间（ratio/baseYear/type 1/2）、叙事时间（Era/Age/Event）。Matrees 的“显示片段 + 绝对年”适合多历法；VVD 的“Ages/Events + Calendar Settings”适合低摩擦；Terrain 的 450 Myr 切片可以成为“古地理层”。三者可以共存：时间线选历法，地图选切片，事件绑定绝对时间。

7.5 协作与发布

本文建议“双层协作”：草稿层用 Yjs/SSE/实时 presence，低摩擦；发布层用 proposal/audit/版本，保证一致性。单人世界默认直编；多人世界再启用提案。发布支持公开页、JSON-LD、OG、静态快照、签名 URL；地图/时间线/卡片是同一世界图的不同视图。

第 9 章 · 结论、贡献与未来工作

9.1 理论贡献

本文把“世界构建”从功能清单提升为三平面耦合问题：模拟平面提供真值，表示平面提供可读性，社会平面提供协作与治理。这个框架解释了一个常见误判：把 Terrain 与 Matrees 直接比“地图好不好看”，会把“表示/策展”的差距误当成“地形算法”的差距；把 VVD 与 Matrees 直接比“谁更先进”，会把“冲突模型不同”误当成“技术水平不同”。

9.2 实践贡献

实践上，本文给出三条可执行路径：① Pro 以真实度上限为目标，输出 SeedPack/MapPack；② Lite 以设备端 512–2048 为目标，用基场+程序化/蒸馏残差；③ Web 以 8–10 秒在线 2048 2D 为目标，用 2C2G 控制面 + GPU worker。三者共享 seed/风格/矢量/provenance，但不共享同一组方程；这使“物理深度”与“低部署成本”不再是对立选择。

9.3 研究限制

本文没有做用户实验，也没有在统一硬件上跑 Matrees/VVD/Terrain 的性能对比；Matrees/VVD 是静态源码+观察，Terrain 是无权重/无输出的源码分析。因此“质量/时延”数字是预算或自报，不是测量。Lite/Web 的模型族是设计提案，尚未实现；8 秒指标依赖缓存骨架，不能外推为“从零生成完整世界”。

9.4 未来工作

  1. 感知实验：同一区域下比较 Pro、Lite、Web、Matrees 风格图，做盲评与任务实验，验证“局部 2048 + 语义层”是否缩小差距。
  2. 误差—成本前沿：用 RMSE/SSIM/海岸偏移/河流连续性与 GPU 秒数，画 Pareto 前沿，决定 Lite/Web 的模型档位。
  3. 4D 时间线：把 0/150/260/450 Myr 切片接入多历法时间线，验证“古地理/纪元”是否提高留存。
  4. 治理实验：比较“实时草稿 + 发布审核”与纯 CRDT/纯提案的冲突率、审核负担与作者满意度。

9.5 总结

世界构建系统不是“地图生成器 + 时间线 + 编辑器”的功能集合，而是三个平面的耦合设计。Matrees 证明了“表示 + 治理”可以做出深度；VVD 证明了“文档 + 实时协作”可以做出低摩擦；Terrain 证明了“物理 + GAN”可以做出真实地形。三者各自的短板，恰好是另外两者的长板。

因此，本文提出的路线不是“做一个更强的 Matrees”或“做一个更地理的 VVD”，而是：用 Terrain 做真值引擎，用 Matrees 式地图/治理做表示，用 VVD 式文档/实时做协作，用 Pro/Lite/Web 做算力分层。Pro 追求真实度上限；Lite 让核显/手机也能生成；Web 用 8–10 秒在线生成标准 2048 2D；2C2G 只做控制面。这样既能保留 Terrain 的物理优势，又能获得 Matrees 的语义/时间/交互/协作/视觉，而不把 2C2G 压垮。
